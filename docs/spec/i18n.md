# Internationalization and the landing page

Idea Cloud ships four UI languages — **ja, en, zh (Simplified), ko** — and a public marketing
page at `/` for visitors who are not signed in.

## Choosing a language

Resolution happens once, in the Worker, before React Router runs (`app/i18n/locale.ts`,
called from `workers/app.ts`):

1. the `lang` cookie, if it names a locale we ship;
2. otherwise the highest-quality match in `Accept-Language` (`zh-TW` and `zh-Hant` both land on
   `zh` — we ship one Chinese dictionary);
3. otherwise **ja**.

The result rides on `AppLoadContext.locale`, so every loader and action can read
`context.locale`. The root loader hands it to `<I18nProvider>`, which is what `useT()` reads,
and to `<html lang>`.

The switcher (`app/components/language-switcher.tsx`) posts to `/lang`
(`app/routes/set-locale.ts`), which sets the cookie and redirects back to the page you were on.
It is a POST on purpose: a prefetch or a crawler must not be able to change someone's language.
The form works without JavaScript.

## Dictionaries

```
app/i18n/locales/<locale>/<namespace>.ts
```

Namespaces: `ai analytics auth common compose errors idea inspiration list lp nav settings`.

**Japanese is the source of truth.** `ja/*.ts` exports a plain object with no type annotation;
`Dictionary = typeof ja`. Every other locale is annotated `Dictionary["<ns>"]`, so adding a key
to Japanese breaks the build until en, zh and ko carry it too. `test/i18n.test.ts` additionally
compares the key shape at runtime and asserts no locale is just a copy of the Japanese.

Copy with a value in it is a function, not string concatenation, so word order stays the
translator's choice:

```ts
count: (n: number) => `${n} 件`;
```

### Using it

- In components: `const t = useT();` then `t.list.empty`.
- Outside React (loaders, actions, `meta`, plain helpers): take the dictionary as a parameter,
  or call `dictionary(context.locale)`. Never call `useT()` outside a component.

### What is _not_ translated

Idea titles and bodies, tags, category names, emails and model ids are user or system data.
They render as stored.

## Landing page

`/` is the public front door (`app/routes/landing.tsx`). Signed in, its loader redirects to
`/app` rather than rendering a second home — the Money Forward pattern the product asked for.
`/login` stays the quiet sign-in gate, and `server/auth/page-gate.ts` is unchanged: `/app/**`
needs a session, everything else is public.

Its visuals are drawn, not photographed. The hero's product shot
(`app/components/landing/app-preview.tsx`) and the feature illustrations
(`app/components/landing/visuals.tsx`) are ordinary DOM and SVG built from the app's own design
tokens, which is what Linear and Vercel show on their own front pages. A screenshot would be one
language, one theme and one pixel density; this stays sharp on any display, weighs nothing to
download, and is in the reader's language — so the shot needs copy of its own, under `lp.preview`.
That copy is staged, not live data. `test/i18n.test.ts` holds the four locales to the same shape,
because a row naming a stage that does not exist would silently fall back rather than fail.

The dark hero and closing band are the only dark surfaces in the product; the app itself stays a
light console. Their styles live at the end of `app/app.css` under the `lp-` prefix. `.lp-dark`
clips its own glow (`overflow: hidden`), so nothing inside it can be `position: sticky` — the
header sits outside it for that reason.

## AI output language

Research, brainstorm, evaluation, discuss and auto-tagging all write in the language of whoever
triggered the run. `server/ai/language.ts` builds the instruction; each prompt is a function of
`locale` rather than a module constant, and `evaluateIdea` / `researchIdea` / `brainstormIdea` /
`discussIdea` / `resolveCreateTags` take an optional `locale` that defaults to Japanese.

The language is fixed **when the text is generated**, because that is when a model writes it.
Switching your UI language afterwards does not rewrite notes you already have — those stay in the
language they were produced in, the same way an idea you typed in Japanese stays Japanese.

### What stays Japanese on purpose

- **The evaluation note's four headings and its `スコア: N` line.** `app/lib/evaluation-notes.ts`
  parses them back out, and a note written today may be read months later by someone reading in
  another language, so they are storage keys, not copy. The prose under them follows the reader,
  and the UI renders the headings from `t.idea.evaluation.section.*` — the stored Japanese is
  never shown raw.
- **Everything sent to TypeSafe Jev**, including the criteria strings and the legend values used
  to interpret the response. That is the model contract. Only the note Jev's answer is rendered
  into is locale-aware.
- **The Jev auto-tag vocabulary** (`server/ai/jev-tags.ts`), which is a fixed curated Japanese
  list. When `TYPESAFE_API_KEY` is set, auto-tags come from that vocabulary and are Japanese in
  every locale; the Workers AI fallback tags in the reader's language. Worth revisiting if Jev
  gains a multilingual vocabulary.

## Errors never cross the language boundary as sentences

`server/ai/*.ts` returns a typed `AiFailure` — `{ status, code, error }` (`server/ai/errors.ts`).
`code` is the value screens render from, via `aiErrorMessage(t, feature, code)` in
`app/lib/idea-ai.ts`. The `error` string stays Japanese and exists only for the HTTP API and MCP
clients that already read it; `/api` responses now carry `code` alongside it so those clients can
localize too.

The rule: **a sentence written where the reader is unknown must not reach a screen.** If you add
a failure path, add a code and a dictionary entry — do not return prose from the server.
